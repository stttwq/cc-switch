# サードパーティ API 利用時に Codex のリモート操作と公式プラグインを保持する: CC Switch 設定ガイド

> 対象バージョン: CC Switch v3.16.1 以降。本記事は現在のコードとユーザーマニュアルにもとづいて整理しており、実際の Access Token や API Key は含まれていません。

## このガイドで解決すること

Codex を使うとき、多くのユーザーには次の 2 つの要望があります。

1. DeepSeek、Kimi、GLM、MiniMax、SiliconFlow などのサードパーティ API、または中継サービス上の GPT モデルを使いたい。
2. Codex 公式アプリのモバイルリモート操作、公式プラグインなどの機能は残したい。

以前は、サードパーティプロバイダーへ切り替えると、旧動作ではサードパーティ API Key が Codex の `auth.json` に書き込まれ、元の公式 ChatGPT / Codex ログインキャッシュを上書きする可能性がありました。これによりサードパーティモデルは使えるものの、公式ログイン状態に依存する機能が消えてしまうことがありました。

現在の動作はこの矛盾を解消しました: **サードパーティプロバイダーへの切り替えは `config.toml` だけを書き、`~/.codex/auth.json` には触れません**。そのため Codex App は引き続き公式アカウントでログインしていると認識しつつ、実際のモデルリクエストは CC Switch で現在選択されているサードパーティプロバイダーへ流れます。サードパーティプロバイダーの API Key ももはや `config.toml` には書き込まれず、ユーザーレベルの環境変数経由で配布されます。

## まず結論

おすすめの手順は次のとおりです。

1. CC Switch の Codex パネルで `OpenAI Official` に切り替える。
2. Codex を起動し、公式 ChatGPT / Codex アカウントで一度ログインする。Free サブスクリプションでも構いません。
3. CC Switch に戻り、サードパーティ Codex プロバイダーを追加、または切り替える。
4. ターミナルを開き直す（新しい環境変数は新しいプロセスでしか読み取れません）、その後 Codex を起動し直し、`config.toml` とモデルカタログを再読み込みさせる。

> ℹ️ 「Codex アプリ拡張」のスイッチはもう一切不要で、ローカルルーティングや接管も不要です——ローカルルーティングの機能群は削除されました。

## 事前準備

次のものを用意してください。

- CC Switch v3.16.1 以降。
- インストール済みで起動できる Codex。app と CLI の両方を入れておくことをおすすめします。
- Codex にログインできる公式 ChatGPT / Codex アカウント。Free サブスクリプションで構いません。
- DeepSeek、Kimi、GLM、MiniMax、OpenRouter、SiliconFlow などのサードパーティ API Key。

`~/.codex/auth.json` の内容を手動でコピーしたり共有したりしないでください。このファイルには公式ログインキャッシュと Access Token が保存されており、機密情報です。CC Switch が読み取るときも、ログイン状態の認識にのみ使い、同期やエクスポートはしません。

## Step 1: OpenAI Official に戻して公式ログインを完了する

CC Switch を開き、上部の `Codex` タブへ切り替えます。まず `OpenAI Official` プロバイダーを選択します。存在しない場合は、プリセットプロバイダーから追加して現在のプロバイダーにしてください。

次に Codex を起動します。CLI の起動がおすすめです。Codex の公式ログインフローに従い、ChatGPT / Codex アカウントでログインします。このアカウントは Free プランでも問題ありません。この構成では、主に Codex App が必要とする公式ログイン ID を保持する役割であり、サードパーティモデルの課金には使いません。

ログイン後、Codex は `~/.codex/auth.json` に公式ログインキャッシュを保存します。以降の重要なポイントは、サードパーティプロバイダー切り替えがこのファイルを上書きしないことです。

## Step 2: サードパーティ Codex プロバイダーを追加する

Codex パネルに戻り、右上のプラスボタンからプロバイダーを追加します。DeepSeek、Kimi、MiniMax、GLM、SiliconFlow などの内蔵プリセットを優先して使うのがおすすめです。

DeepSeek を例にすると、プリセットを選んだ後は API Key を入力するだけです。プリセットは base URL とデフォルトモデル一覧を自動で構成します。

> ⚠️ **重要な変更**: CC Switch はリクエストプロトコルを変換しなくなりました。サードパーティプロバイダー自身が、Codex が直接話せる endpoint（`wire_api = "responses"`）を提供している必要があります。OpenAI Chat Completions endpoint のみを公開しているプロバイダーは、プロバイダー側で Responses 互換の入口を用意しない限り Codex では使えません——初期バージョンはローカルルーティングでプロトコル変換をしていましたが、その能力は削除されました。

## Step 3: サードパーティプロバイダーへ切り替えてターミナルを開き直す

Codex プロバイダー一覧に戻り、先ほど追加したサードパーティプロバイダーを有効化します。切り替えが完了したら:

1. **ターミナルを閉じて開き直す** —— サードパーティプロバイダーの Key はユーザーレベルの環境変数 `CC_SWITCH_CODEX_API_KEY` に書き込まれるため、起動中のターミナルは新しい値を読み取れません
2. Codex を再起動 —— Codex は起動時に `config.toml` を読み込み、`/model` メニューも通常は再起動後にモデルカタログを再読み込みします

開き直した後は、簡単に確認できます。

- Codex App ではアカウント情報が引き続き公式アカウントとして表示される。これは期待される動作です。
- CC Switch では現在の Codex プロバイダーがサードパーティプロバイダーになっている。
- サードパーティプロバイダー側のダッシュボードや残高記録に実際のモデルリクエストが表示される。

## 仕組み

Codex の設定は主に 2 つのファイルに分かれています。

```text
~/.codex/auth.json
~/.codex/config.toml
```

この 2 つは役割が異なります。

- `auth.json` は公式 ChatGPT / Codex ログインキャッシュを保存します。Codex App が公式アカウント、リモート操作、公式プラグインを認識するために必要なログイン材料です。
- `config.toml` は現在のモデルプロバイダー、base URL、モデル、モデルカタログなどの実行時設定を保存します。

サードパーティプロバイダーへ切り替えると、CC Switch は `config.toml` だけを書き込みます。

```toml
model_provider = "custom"

[model_providers.custom]
name = "DeepSeek"
base_url = "https://api.deepseek.com"
wire_api = "responses"
env_key = "CC_SWITCH_CODEX_API_KEY"
```

`env_key` はキー値ではなく**変数名**です。実際の API Key は Windows 資格情報マネージャーに保存され、切り替え時にユーザーレベルの環境変数へ書き込まれます。同時に `auth.json` は公式ログインキャッシュを保持したままです。そのため Codex App 側では公式アカウントを認識でき、モデルリクエストは `config.toml` の現在の provider と base URL に従ってサードパーティ API へ直接接続します。

> 💡 `base_url` はこの方式で唯一の例外です。Codex CLI はこのフィールドでの変数参照に対応していないため、現在アクティブなプロバイダーのアドレスは `config.toml` に平文で書き込まれ、それ以外のプロバイダーのアドレスは引き続き資格情報マネージャーの中にだけ存在します。

もうひとつの安全扉があります。ある `[model_providers.*]` テーブルが `requires_openai_auth = true` を持ちながら自身の資格情報（`env_key` も token も）を欠いている場合、CC Switch は**書き込みを拒否します**——そのままでは Codex が `auth.json` 内の公式ログイン資格情報でサードパーティのアドレスへアクセスし、公式資格情報を漏らしてしまうためです。そのプロバイダーに API Key を補うか、このフォールバック指示を取り除いてください。

## 理解しておくべき副作用

### Codex 内の表示アカウントは公式アカウントのまま

ここが最も誤解されやすい点です。Codex App は `auth.json` 内の公式ログイン状態を見るため、公式アカウント情報を表示し続けます。

ただし、これはモデルリクエストが公式 OpenAI に流れているという意味ではありません。実際の通信先は、CC Switch の現在の Codex プロバイダーと `config.toml` で決まります。

### Codex のアカウント表示で課金先を判断しない

DeepSeek に切り替えた場合でも、Codex には公式アカウントが表示されます。しかしモデルリクエストは DeepSeek API へ送られます。課金、上限、エラーコード、データポリシーはサードパーティプロバイダー側の仕様として理解してください。

### モデルマッピングを変更したら Codex を再起動する

Codex のモデルカタログは起動時に読み込まれます。CC Switch が新しいモデルカタログを生成していても、実行中の Codex がホットロードするとは限りません。モデルマッピングを変更した後は Codex を再起動してください。

## よくある質問

**サードパーティ API に切り替えたのに、なぜ Codex はまだ公式アカウントを表示しますか？**

これは期待される動作です。公式アカウント情報は `auth.json` から取得され、実際のモデルプロバイダーは `config.toml` と CC Switch の現在のプロバイダーで決まります。

**Free サブスクリプションで本当に大丈夫ですか？**

大丈夫です。ここでの公式アカウントは、Codex App が必要とする公式ログイン状態を取得・保持するために使います。サードパーティモデルリクエストは、CC Switch に設定したサードパーティ API Key を使います。

**有効化しても公式プラグインやモバイルリモート操作が使えない場合は？**

まず `OpenAI Official` に戻し、Codex を再起動して一度公式ログインを完了し、その後あらためてサードパーティプロバイダーへ切り替えてください。切り替え自体は `auth.json` を上書きしないため、ログイン状態は通常やり直す必要がありません。

**サードパーティリクエストが 404 になる、モデル一覧が違う、ストリーミング応答がおかしい場合は？**

そのプロバイダー自身が Responses 互換の endpoint を提供しているかを確認し（CC Switch はもはやプロトコル変換をしません）、次に `config.toml` 内の `base_url` と `model_provider` が同じテーブルを指しているかを照合し、最後にターミナルを開き直したかを確認してください（`CC_SWITCH_CODEX_API_KEY` は新しいプロセスでしか参照できません）。それでも異常が残る場合は [5.4 環境変数の競合](../user-manual/ja/5-faq/5.4-env-conflict.md) を参照してください。

**サードパーティ利用中に OpenAI Official へ戻せますか？**

戻せます。切り替えは通常の操作であり、以前の「接管が公式への切り替えを阻止する」という制約はありません——あのローカルルーティングは削除されました。公式へ戻った後も同じくターミナルを開き直してください。
