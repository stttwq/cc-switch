# 实施方案：安全边界加固与供应商编辑按需更新 1Password

- **状态**：待施工；本文件是交给施工模型的实施规范，不代表修复已完成。
- **审查日期**：2026-09-28。
- **代码基线**：`1password` 分支，`c9333e86846ca957d858c784425692c0ebc68d41`，版本 `2.3.1`。
- **工作范围**：只读代码审查与方案编写；不修改业务代码，不调用真实 1Password，不修改保险箱、注册表、用户配置或远端同步数据。
- **分支约束**：沿用既有自用分支策略，不合并 `main`，不自动发布，不自动提交。
- **历史方案关系**：既有凭据迁移、严格投递、同步/SQL 边界方案继续有效；本文件只补充当前版本发现的问题。历史方案中的“待施工”或旧问题描述不能代替当前代码证据。
- **定位方式**：下文行号以本基线为准；施工前按文件路径及函数名复核。审查隔离工作树可能落在 `main`，必须先核对 HEAD，不能在旧工作树上实施。

## 1. 目标及交付边界

### 1.1 用户要求

1. 检查项目的安全性，提供具体问题、触发前提、关键位置、修复理由和验收办法。
2. 普通供应商编辑中，**只修改模型、推理等级、备注、排序、图标等非凭据配置，不应请求 1Password**。
3. 供应商名称、Base URL、API Key 的有效变化才进入相应的 1Password 更新流程。
4. 交付详细文件，供其他模型施工；本轮不实现业务改动。

### 1.2 “同步”必须分清三件事

- **1Password 条目更新**：CCS 调用本机 `op` 读写条目；用户这次要减少的是这条路径。
- **1Password 自身跨设备同步**：由 1Password 管理；CCS 无法承诺其内部同步次数或完成时间。
- **CCS WebDAV / S3 配置同步**：负责共享模型等非秘密配置，与条目更新是两条独立链路。不得为了减少 `op` 而禁用正常的本地保存或配置同步逻辑。

验收同时记录：前端 IPC 调用次数、`SecretVault` 逻辑调用次数、真实 `OpRunner` 子进程次数。三者不是同一个数字，不能用“只调用一次 put”冒充“只启动一次 op”。

### 1.3 零调用的覆盖范围

“只改模型 = 0 次 op”覆盖：打开编辑框 → 表单初始化 → 提交 → 数据库存储 → 当前供应商 live 配置更新 → 关闭编辑框 → 列表/状态刷新。

以下显式动作不纳入这条零调用承诺：用户点击显示密钥、启动终端、实际切换需取凭据的供应商、手动补齐/修复引用、手动刷新端点、凭据迁移、显式保存秘密字段。必须在界面上区分这些动作，不能在普通编辑副作用中偷偷触发。

## 2. 总体施工原则

1. **先写失败测试，再修复。** 每个确认问题有独立复现样本；次数测试断言精确的 `0`，不能用宽松的上界遮掩多余访问。
2. **不靠前端 dirty 状态建立安全边界。** 前端表达用户意图，后端以规范化的数据和已保存状态决定差异；所有写入入口共享相同的后端规则。
3. **配置保存与凭据读写分离。** 常规非秘密编辑不得为比较 API Key 而先从 1P 取钥匙；不得把“先取出整包，再发现无需更新”当作优化完成。
4. **不新增持久密钥缓存。** 不把 API Key 写进 DB、端点缓存、浏览器存储、表单默认值、Query 缓存、日志或临时文件，也不为比较密钥新增持久哈希。
5. **未知不等于空。** 省略、未加载、保留、显式替换、显式清除必须可区分。读失败、锁定、权限拒绝、条目冲突不得降级为空包继续覆盖。
6. **不丢失其他秘密。** `extra_env`、敏感请求头及既有条目字段不能因为只关注三项而被整包覆盖清空；模型专用编辑应完整保留这些字段。
7. **1P 仍是凭据和端点的持久真源。** 本地端点只用于显示和不取钥匙的配置投影；实际给 CLI 注入钥匙时，钥匙和端点必须来自一致的已验证来源，不能用过期缓存盖掉新真值。
8. **保留既有安全保障。** 严格投递、foreign 环境变量拒写、op 签名校验、条目归属核验、stdin 传秘密、同步/导出秘密裁剪全部保持。
9. **最小改动，按阶段可验收。** 不顺手重构全部 Provider 类型，不重做凭据框架，不引入通用任务系统，不默认改同步协议。
10. **跨系统写入不伪装成事务。** 1P、SQLite、live 文件无法共同原子提交；区分保存失败、已保存但投递待重试、结果不确定。不得通过删除原条目“回滚”编辑。
11. **远端数据不是本机授权。** SQL、WebDAV、S3、归档、原生文件中的开关或路径不能自动成为执行命令、发送本机凭据或写任意文件的授权。
12. **安全结论分级。** “静态代码确认”“攻击链需验证”“纵深加固”“历史有意边界”分开，不把依赖版本或单个危险 API 的存在直接等同于漏洞。

## 3. 审查方法与覆盖限制

本次重点审读供应商编辑和凭据调用链、1Password 后端、同步/SQL 数据边界，以及导入数据到本机执行/文件写入的路径。另检查了依赖审计配置和安全文档。

本次**没有**运行全量单元测试、真实 1P 集成测试、安装/卸载虚拟机测试、在线依赖公告核验、历史秘密全量扫描或远端渗透测试。因此：

- 代码中可达的数据流可以作为静态确认缺陷；涉及 Windows 实际执行或网络行为的完整复现仍应在隔离测试环境验收。
- 不宣称“项目没有其他漏洞”或“依赖没有已知漏洞”。
- 不将旧方案已经修复的问题重复列为本版缺陷。
- 当前存在的未跟踪 `.zcodeignore` 与本任务无关，不修改、不清理。

## 5. 已确认的凭据安全问题与修复规范

这里的“确认”指当前基线的静态可达调用链已经核实，不表示已对真实保险箱实施攻击。P0 表示本项目应优先止血的凭据泄露/越组修改/误归档问题，不等同于互联网远程无交互 RCE 等级。

### SEC-01：按 item ID 读取、改名、删除缺少统一归属核验（P0）

**关键位置**：

- `src-tauri/src/database/snapshot_policy.rs:350–380`，`merge_secret_refs`：本机无同键引用时，可采纳同 vault 的远端引用；只检查供应商存在，不证明 item 属于它。
- `src-tauri/src/secrets/onepassword.rs:520–530`，`fetch_item_resolved`：引用 ID 直达成功后只检查是否归档，随后解析秘密包。
- 同文件 `:595–634`，`put_inner`：使用前述结果改标题和托管字段。
- 同文件 `:390–435`，`retitle_managed_items`：只检查 vault、占位 ID 和归档状态，没有核验 group。
- 同文件 `:1453–1458`，`delete`：引用 ID 直接归档，没有读取归属。

**触发与影响**：用户导入了构造过的 SQL，或采用了攻击者能够修改的非 E2E 同步载荷，其中新供应商的引用指向同 vault 的另一个条目。之后对新供应商执行需要取钥匙、保存、对账标题或删除的操作，可能读出、改写、改名或归档其他组的条目。攻击者须能提供/修改导入数据并知道可用 vault/item 标识；不是仅访问一个网页就能无交互取钥匙。E2E 能降低服务器篡改入口，但不能让导入引用本身成为可信授权。

**为什么现有保护不足**：`onepassword.rs:542–547` 已经对标题兜底唯一命中检查归属；它不保护 ID 直达、独立改名和删除路径。vault 相同只能证明处于同一个保险箱，不能证明属于当前供应商。

**施工要求**：

1. 提炼单一条目身份核验函数，对已取得的 JSON 验证预期 `SecretGroup`、未归档状态、响应 ID 一致性，并在响应包含 vault 信息时验证 vault 一致。
2. 所有读取结果在解析并向业务层返回秘密前核验；冲突解析最终 get 的响应也重新核验。读取和普通保存路径复用已经取得的 JSON，不为校验额外请求 op。
3. 1P 新格式条目必须精确匹配 `cc-switch-group`。归属缺失、格式错或不匹配不得静默“修正”为当前组再写回，不得把失败降级成空包。
4. 旧格式无 group 的兼容规则必须明确：最多沿用现有可证明归属的旧格式专属标识进行受限读取；普通编辑、改名和归档不得凭裸显示名认领。不能证明的条目转为人工修复，不牺牲安全来保证零提示。
5. 对删除和对账改名，先定位并核验真实条目，再按核验后的 ID 操作；不能直接拿导入 ID 归档。显式破坏操作增加必要 get 是允许的，不受“模型编辑零 op”限制。
6. 同步导入继续零 op，可保留同 vault 的结构引用作为定位候选，但引用不等于授权。引用字段清单不能作为真实钥匙有效的证明；界面应区分“引用已关联”和“凭据已验证”，至少不可在未取值时宣称已验证。
7. 修复/重建引用也调用相同身份规则，避免一条修复路径把另一条校验绕开。

**验收**：使用 FakeOpRunner 与内存 DB，构造同 vault 的 A/B 供应商、跨 app、AppSync、归属缺失、归属错误、响应 ID 不一致和归档条目。导入恶意引用后 fetch 不返回他组秘密，put/retitle/delete 不产生他组写操作；读取/保存已有合法条目的核验不增加 op 次数。测试必须覆盖从导入合并进入使用的完整链路，而非只测纯函数。

### SEC-02：删除的标题兜底可归档其他应用的同名条目（P0）

**证据**：`onepassword.rs:1450–1475` 的 `delete` 与读取采用不同逻辑，`:1461–1464` 对候选标题直接执行删除；候选包含裸显示名。`services/provider/mod.rs:725–728` 的正常删除先处理 vault 再删除 DB，因此该路径可由普通 UI 删除触达。

**触发**：待删供应商引用缺失或已失效，保险箱只有另一应用的同名旧格式条目。裸名称候选唯一命中，删除成功，不会进入只在同名冲突时才有的归属检查。无需恶意 SQL 即可发生。

**实施**：与 SEC-01 共用安全定位器；废弃“按标题直接 delete”。对不匹配归属的候选不得删除；继续查找合法候选或报告该组没有可安全归档的条目。禁止因为安全校验失败而自动清空引用/删除真实条目。保持已不存在的合法目标可幂等处理。

**验收**：Claude/Pi 同名、裸标题唯一命中他组、新/旧标题混用、引用失效且标题归属不明；断言他组 ID 不出现在任何 archive/delete 调用中。测试不能只覆盖冲突时返回两个条目的情况。

### SEC-03：孤儿识别仍按旧标题，在用条目被列为可清理对象（P0，误归档）

**证据**：`services/provider/mod.rs:346–360` 的 `list_onepassword_orphans` 只构造 `cc-switch/<app>/<id>` 作为在用标题；本版实际首选标题已是 `<app>/<显示名>`。`:407–412` 的 `cleanup_onepassword_orphans` 直接归档用户确认的 ID，没有重新判定仍是孤儿。

**影响**：当前新建或已对账改名的在用条目会被列为“孤儿”，用户信任清理界面并确认后，真实凭据条目被归档。条目通常可在 1P 恢复，因此不要写成不可恢复永久删除；但所有依赖它的终端和配置会不可用。

**实施**：

1. 先以本机 `secret_refs` 中当前 vault 的真实 item ID 集合识别在用条目，与显示标题彻底解耦。AppSync 同样以身份保护，不能仅依赖字符串标题。
2. “无本地引用”不自动等于孤儿：新设备、引用丢失、另一设备尚未同步到本机的条目均可能仍在用。结构列表不足以证明归属时标成“未知/待核验”，默认不勾选、不自动归档。
3. 本机不存在该 provider 的 group 也未必是整个共享 vault 的孤儿。缺少本机明确删除记录时，应作为手动高级清理候选，明确展示其 group、item ID、vault 及不确定原因，不能称“安全可删除”。
4. 使用现有显式删除后的 orphan 待重试记录作为更强依据，但在实际重试前仍检查该 provider 是否已被重新创建、引用是否恢复；新建/恢复后的在用对象不得再次归档。
5. 用户提交后在后端重新检查在用引用及身份，拒绝已经变成在用、归属变化或不在本次合法候选范围的 ID。前端的确认列表不是后端永久授权凭证。
6. 保持归档而非永久删除，不新增自动清空保险箱功能；修复前暂停使用现有“孤儿清理”处理新标题条目。

**验收**：新标题、旧标题、改名、重复标题、AppSync、无 ref 但仍属于现有 provider、其他设备独有条目、列出候选后重新关联、删除后重新创建、重复提交等全部覆盖。在用条目 archive 次数必须为 0。

### SEC-04：原始 op 调试输出是条件性泄露面（P2，纵深加固）

**证据**：`onepassword.rs:824–827` 只检查 `CC_SWITCH_OP_DEBUG` 环境变量是否存在，就把完整 args 和原始 stderr 输出到控制台；即使值为 `0` 也会启用。

**边界**：本次未证明生产 op 的某条错误必然回显密钥，因此不将其等同于已发生的秘密泄露。但错误原文不受 CCS 控制，身份/路径/字段上下文可能进入日志，且这与默认的“stderr 不外泄”承诺不同。

**实施/测试**：发布构建不允许打印原始 stderr；仅保留错误分类、退出状态、耗时和不含值的操作类型。若必须保留开发调试，则编译时限制且输出脱敏。用包含假 token/URL userinfo 的错误样本验证日志和错误 IPC 均不含原文。不能使用真实钥匙作为 fixture。

### SEC-05：外部 SQL 可携带触发器，绕过本机数据保留策略（P1，高优先级）

**已核实证据**：`database/backup.rs:67–78` 的 `import_authorizer` 主要阻止越出暂存文件的操作，未拒绝 `CreateTrigger`；`:374–381` 执行完外部 SQL 就卸载 authorizer；`:744–768` 只验证必需表存在；`:417–420` 随后在该暂存 schema 上回填本机数据并把整库复制为主库。

**触发与影响**：攻击者在合法格式的 SQL 中添加作用于 `secret_refs` 或 `settings` 的插入触发器。之后 `snapshot_policy.rs:362–365` 向暂存库回填本机引用时，触发器能改写刚回填的值；因此“本机优先、远端不能覆盖已有引用/设备本地设置”失效，触发器还可随 Backup 留在主库。叠加 SEC-01 能把原本仅影响新引用的问题扩大到已有本机引用。

这不是 `ATTACH`/`VACUUM INTO` 任意文件写入漏洞，这些已有 authorizer 防护；真正的问题是**暂存 schema 中的可执行逻辑会在本机可信数据回填阶段继续执行**。旧注释关于“唯一边界是临时文件”的前提在引入本机数据合并后已不成立。

**本轮验证程度**：除调用链静态核实外，使用 Python SQLite `:memory:` 验证了 AFTER INSERT trigger 能将模拟回填的可信 item ID 改成另一合成 ID；未运行项目真实导入流程，没有修改主库。此结果是 SQL 语义复现，不冒充应用端到端测试。

**实施**：

1. 外部 SQL 执行阶段禁止创建 trigger、临时 trigger、未经应用声明的 view/虚拟对象；使用 SQLite authorizer，不用关键词正则。
2. 在任何迁移、回填或复制前审查 `sqlite_schema`，拒绝不受支持的可执行 schema 对象；这是对二进制 `.db` 恢复的必要补充，因为它不经过 SQL 文本 authorizer。
3. 校验已知表/列与对象类型，防止“名称存在但定义不可信”。不得允许导入文件自报 schema 版本就跳过检查。
4. 保留最小修复与更强边界的阶段差异：先阻断 trigger/view 等已确认入口；若支持的历史 schema 复杂，优先把经校验的普通数据行复制到**由程序自身创建的干净暂存 schema**，再执行本机数据保留策略，而不是对任意导入 schema 做本机回填。不要只禁止 CREATE TRIGGER 后就宣称所有不可信 schema 风险已消除。
5. 不因新增拒绝规则静默丢弃有问题的对象后继续成功；给出可读错误和安全恢复路径，主库保持不变。历史正常导出必须有回归样本。

**验收**：合法 SQL + 影响 secret_refs 的触发器、影响设备本地 settings 的触发器、二进制带触发器备份、同名 view/异常表定义均拒绝；主库与本机值不变；正常旧版 SQL、空业务表导出及当前备份恢复仍成功。用合成 ID/配置值即可复现，不需要真实 op 或恶意可执行命令。此修复与 SEC-01 各自独立测试，不能用其中一个通过掩盖另一个缺口。

### 6.2 行为矩阵（推荐默认，不等待新增产品决策）

| 用户动作 | 是否调用 1P | 处理 |
|---|---:|---|
| 打开/取消编辑；完全无变化保存 | 否 | 显示本地非秘密数据；不自动显示钥匙 |
| 仅模型、模型列表、推理等级、上下文长度、备注、图标、排序 | 否 | 保存配置并走不取凭据的 live 投影 |
| Base URL 未编辑，或普通 URL 规范化后等于本地已显示值 | 否 | 保留 1P 当前端点；不把缓存值回写成真值 |
| 显示名称有效变化 | 是 | 精确定位并核归属，更新标题；保留全部值 |
| Base URL 有效替换/明确清除 | 是 | 更新相应字段；成功后才更新/清除本地缓存 |
| API Key 保留/未加载/占位引用 | 否 | 不取钥、不将占位字符串存为新密钥 |
| 用户明确提交新 API Key | 是 | 一个显式秘密更新；取到旧包后若相同可省 edit，但不能承诺零 get |
| 用户粘贴的 API Key 恰好与 1P 旧值相同 | 允许一次读取判等 | 后端没有旧明文时，不可能既零读取又证明相等；不得用持久哈希绕过这个限制 |
| 用户明确清除 API Key | 是或按业务规则拒绝 | 单独确认；需要 key 的供应商不可静默变成可用状态 |
| 显示名改变但真实条目不存在 | 是，返回待关联/修复 | 不因纯改名创建空凭据条目，不凭同名认领其他条目 |
| 修改 provider ID | 不视为改显示名 | 这是身份迁移，保持既有限制并单独测试，不能走 rename-title 捷径 |

**其他秘密字段的处理默认值**：用户的“三字段触发”适用于常规编辑。对 `extra_env`、敏感 header、其他提取出的秘密，普通配置提交只允许保留；若检测到新增/替换/删除，明确拒绝该提交并提示使用独立的“高级凭据”显式保存入口。该入口有明确的 1Password 提示，允许更新它负责的秘密。这样既不让模型编辑唤醒 1P，也不静默丢秘密或将秘密降级存入 DB。不要为了字面上的“只有三字段”让其他秘密永远无法安全维护；本阶段可先拒绝并提示，不必额外做复杂编辑器。

## 7. 按需更新的具体施工设计

### 7.1 前端：提交意图而非回灌的整包秘密

关键文件：`EditProviderDialog.tsx`、实际 Provider 表单/字段组件、`src/lib/api/providers.ts`、Provider update 的 TypeScript 类型与测试。

1. 保留 Base URL 的显示，但将“初始显示值”和“待提交替换值”分离。对话框切换 provider、关闭重开时重置意图；列表后台刷新不得把用户正在编辑的值重置。
2. API Key 使用显式状态：`keep`、`set(value)`、`clear`。空输入默认 keep；clear 必须独立按钮/意图。reveal 只影响展示，不自动变成 set；禁止 reveal 值进入表单初始快照。
3. Base URL 同样用三态。对于未能从本地读取的敏感 URL，显示“已配置，未读取”，而非把空白理解成清空。
4. 名称保留普通配置字段，由后端比较新旧有效名称；禁止仅靠前端 `nameDirty` 控制标题更新。
5. 新增独立 update payload（示意，不要求照搬命名）：`{ providerConfig, credentialPatch: { apiKey, baseUrl }, expectedConfigVersion? }`。不要把值包装进 `meta` 或 `settingsConfig` 再持久化。
6. 可选的并发版本使用仓库已有可靠版本机制；没有则在后端锁内重读旧值并对关键字段做预期值校验，不为本任务盲目新增全库版本系统。过期表单的冲突提示不得含钥匙。
7. 表单状态、mutation 参数、错误调试工具均不打印秘密；关闭对话框丢弃相关状态。JS 无法保证物理内存归零，不作该承诺。

### 7.2 后端：纯提取 → 分类 → 零调用配置分支/显式凭据分支

关键文件：`commands/provider.rs`、`services/provider/mod.rs`、Pi 对应 `services/provider/pi.rs`、`secrets/extractor.rs` 与 `secrets/vault.rs`。

1. **保留纯提取能力**：先从提交中剥离所有已知秘密，再形成待存的 sanitized config；不能在“没改三字段”时直接绕过 sanitizer，把原始 JSON 写进库。
2. 提取与持久化解耦：`strip_and_store_provider_secrets` 当前把两者绑定，编辑应拆为纯提取/验证和有条件持久化两步。新增、迁移、导入的语义分别保留，不用一个 `skip_vault` 布尔到处传来传去。
3. 在现有 app 切换锁内加载当前 provider/引用/非秘密端点，比较有效名称；普通端点只对显式 set 做安全、最小规范化比较。若 endpoint 未加载/未知，不得把 `None` 当成真实空值。
4. 对 legacy 全量配置更新：不可信 dirty 提示不能授权写凭据；旧入口的真实秘密仍必须剥离并进入显式兼容路径或明确拒绝。至少覆盖当前所有前端和 Pi 写入调用者；不能改变默认参数让旧调用者悄悄清空秘密。
5. `nameChanged == false` 且 patch 全 keep 且无其他秘密变更时：只写 sanitized config，vault 的 fetch/put/delete/status 全为 0。
6. 只有名称变化时，不能让 `new_bundle.is_empty()` 或 `bundle == old_bundle` 吞掉标题更新。标题使用新显示名显式传入，不在 DB 更新前再次查旧显示名。
7. 多字段同时变化合为一次请求，基于同一份经过身份核验的 1P JSON 合并；未变的 api_key、base_url、extra_env、header 及用户自建字段保持。
8. 对已保存且引用声称存在的条目，fetch 返回 None 不应自动用空包替代再创建。明确区分新增、已有条目丢失、未配置凭据；仅真正新增且用户显式提供所需凭据才允许 create。

### 7.3 1P 原子粒度：一个安全的 read-modify-write，不重复取包

推荐在 `SecretVault` 增加语义明确的 patch/update 操作（具体命名遵循仓库），由 Legacy Windows 实现保持兼容，1P 实现在同一次定位取得的 JSON 上更新：

1. 按安全定位器读取一次（SEC-01）。
2. 对新标题和目标字段逐项计算差异。全相同时返回 unchanged，不发送 edit。
3. 只改显式目标字段，保留其他字段和条目元数据，stdin 传完整编辑 JSON。
4. 返回最小结果：是否变更、更新后的引用字段清单、可安全缓存的端点等，不把整包回传到前端。
5. 对可靠 ref 命中的常规路径，**目标为 1 次 get + 至多 1 次 edit**。查找旧标题/冲突的额外调用单列；不要为了硬凑数字跳过归属验证。现有 op 字段删除可能需要额外 `[delete]` 调用，清除路径须单独定义并测试，不谎称所有场景固定两次。
6. 最小可交付先做到“未改凭据精确 0 次”，再去除变更路径重复 get；不得把第二步微优化变成第一步的前提阻塞。

**并发**：现有 `OP_LOCK` 只串行单次 op，不等于整个 read-modify-write 事务。使用当前 app/组更新互斥保护本进程同组更新，制定固定锁顺序，避免在已持有 OP_LOCK 时重复获取。1P 桌面或其他设备仍可并发修改，不能声称本地锁解决跨设备丢更新。若 op/条目版本有受支持的条件更新语义，先通过文档或隔离实测确认后再用；否则记录 best-effort 边界，更新前读取最新 JSON，结果不确定时提示重新核对，不盲目重试 create。

### 7.4 live 投影：零 op 不能以丢配置为代价

关键文件：`services/provider/live.rs`、`services/provider/pi.rs`、`resolve_base_url` 及其调用者。

- 增加明确的“配置编辑、禁止取凭据”的投影上下文或专用函数，不能用全局开关改变所有 resolve 行为。
- 对既有当前 provider，更新模型字段时保留现有环境引用与属于该 provider 的端点；只使用本地已知安全端点或已验证属于该 provider 的 live 片段。
- 缓存 miss、敏感端点不缓存、live 中无法证明端点归属时，不得偷偷 fetch，也不得删掉 endpoint 让 CLI 落回默认主机。安全保留既有投影，或将本地配置标记为“已保存，live 待显式应用”，让用户主动执行需要取 1P 的动作。
- 用现有 pending/警告机制表示部分完成；仅在不存在合适机制时增加最小返回状态。不得只在日志中 warning、前端仍显示完全应用成功。
- Pi 必须只投影当前被编辑的 provider，不扫描全部 provider 并逐个取钥。保留其他 provider、MCP、外部字段及官方认证语义。
- 真正启动终端/切换需读取钥匙时仍走安全 fetch 并校正端点，不因模型编辑零调用改变凭据投递安全规则。

### 7.5 写入顺序与部分失败

当前 `store_provider_bundle` 先写端点缓存再访问 vault，必须改正：

1. 后端校验及纯提取成功后才做外部副作用。
2. 无凭据差异时仅 DB 配置保存与零 op 投影；不改引用和 endpoint 缓存。
3. 有凭据差异时先安全更新 1P；成功后在可用的本地事务边界更新 provider、secret_refs、endpoint。端点由普通变敏感或被清空时删除旧缓存，不能保留旧普通 URL。
4. vault 失败/取消：不写新端点缓存，不改 provider/引用，不投影 live。若服务端可能已提交但客户端超时，返回“结果不确定，需要核对”，不能谎称一定没改。
5. 1P 成功但 DB 失败：保留原条目，不归档、不清空钥匙；提示“1P 已更新，本地保存失败”，允许明确重试/修复。不要把秘密写进 pending 记录。
6. DB 成功但 live 失败：返回已保存与待应用状态，重试仅做必要投影，不能重新改 1P。
7. API Key 与 Base URL 同时变更必须使用同包结果，不得出现新钥匙配旧端点。UI 不允许失败后继续显示“全部同步成功”。

### 9.2 安全与失败注入

1. **归属**：恶意导入 ref → fetch/patch/delete/retitle；他组条目不可用、不可改、不可归档。
2. **孤儿**：新旧标题均在用；共享 vault 上另一设备独有；预览后重新引用；待重试删除后恢复 provider。
3. **SQL**：合法头加触发器、二进制 trigger、异常 schema，均在主库替换前拒绝；旧正常备份仍可导入。
4. **凭据失败**：锁定、取消、NotFound、冲突、无签名、网络错误；检查 DB/cache/ref/live 的每一步状态。
5. **部分成功**：op edit 成功后 SQLite 失败；DB 成功后 live 失败；Pi native 已改但 DB 与 native 回滚都失败。必须明确报告阶段，禁止“已经回滚”泛称。
6. **重试**：`src/lib/query/mutations.ts:109–158` 当前完整 variables 重试需要阶段化处理；不能让“重试 live”重新提交旧 key/URL 覆盖新远端状态。
7. **并发**：同 provider 两窗口，编辑与切换、删除/维护并发；在任何远端修改前检查过期请求，锁顺序固定。跨设备限制写入文档。
8. **泄露**：合成秘密标记不得出现在 SQLite、导出 SQL、日志、IPC 错误、argv、临时模板文件。额外字段/带凭据 URL 同样覆盖，不只测典型 API Key 前缀。
9. **授权**：配置专用操作即使 vault 模拟为 Locked，也应在不调用它的前提下保存成功；不能靠预先解锁才能通过测试。

## 10. 额外可靠性加固与尚未完成的审查范围

### 10.1 op 超时覆盖盲区（P2，可靠性）

`onepassword.rs:773–797` 在启动 stdout/stderr 读取线程和建立 deadline 前，同步写 stdin，且忽略写入错误。若子进程不读输入或管道互等，宣称的 120 秒超时可能无法覆盖这一阶段。

后续修复从 spawn 前建立统一截止时间，并发处理管道；写入/读取/等待错误明确传播，超时清理子进程与线程。用受控子进程模拟不读 stdin、输出阻塞、提前退出；不要用真实 op 制造卡死。此项不是已证明的远程 DoS 攻击，不与凭据越组漏洞混为一谈。

### 10.2 已抽查但未确认漏洞的边界

- **同步归档**：`services/webdav_sync/archive.rs:68–134` 使用新暂存目录、`enclosed_name()`、条目数限制和实际解压字节预算；未发现可证明的常规 Zip Slip。没有还原 symlink 的行为，不能仅因为未看到 canonicalize 就报漏洞。Windows 特殊名称/重解析点竞争未动态验证。
- **E2E**：`services/sync_e2e.rs:367–434,461–498` 已有格式/KDF 校验、AEAD、AAD 和相关哈希检查。SEC-01/05 不代表可以无口令伪造合法 E2E 快照。
- **TLS**：`services/http_client.rs:117–154` 未关闭证书校验；支持显式配置 HTTP 不能单独等同于 TLS 绕过。传输/重定向的全部组合未完成动态测试。
- **SQL 沙箱既有保护**：ATTACH、VACUUM INTO、虚拟表和危险 PRAGMA 的拒绝仍有价值；SEC-05 是另一层 schema 执行边界，不能替代既有防线。
- **列表读取**：`commands/provider.rs:52–99` 通过引用结构和端点缓存提供状态，当前并非批量读钥匙的根因，应保持这条零调用路径。
