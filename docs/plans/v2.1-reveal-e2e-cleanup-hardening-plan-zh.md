### 1.2 目标

1. 编辑任一供应商（Claude / Codex / Pi）时，Base URL 框**默认就显示**当前值（它本来就允许回显，只是断链）。
2. API Key 框默认仍是遮罩，但提供"显示"按钮：点击后从凭据管理器按需读一次、明文显示在输入框里；可再点隐藏。
3. 卡片上显示 Base URL（主机名部分即可），让用户不进编辑页也知道切到了哪个端点。
4. 回显不得把密钥值留在任何缓存、日志、DB 或 live 文件里。

### 1.3 原则调整（必须写进瘦身方案与 SECURITY.md）

原则 3.1-3 从"前端零密钥"改为：

> **前端默认零密钥**：批量读取（列表、卡片、托盘）永不携带密钥值。密钥值只在用户**显式点击"显示"**时、针对**单个供应商的单个字段**、经专用命令按需回传一次；前端不得把它放进 React Query 缓存、localStorage、表单初始值快照或任何日志；对话框关闭即丢弃。

为什么这样改而不是整个放开：用户要的是"编辑时看得到"，不是"列表里带着"。按需 + 显式点击把暴露窗口从"任何时候前端内存里都有全部密钥"缩到"用户正在看的那一个"。这也和 1Password / Windows 凭据管理器控制面板的行为一致。

### 1.4 做法

#### 1.4.1 后端：新增一个回显命令

```
reveal_provider_secret(app: String, provider_id: String, field: "api_key" | "base_url") -> Result<Option<String>, String>
```

- 放在 `commands/provider.rs`，**`async fn`**，内部 `state.secrets.get(target)`，把 `Zeroizing<String>` 转成返回值后立即丢弃本地副本。不接受 `field = "env/<VAR>"`（extra_env 不回显，Claude 的 `OPENROUTER_API_KEY` 这类用户自写敏感 env 保持"只显示名字"；要改值就整体重填）。
- 读之前校验供应商存在于 DB（防止用命令探测任意 target）。
- 日志：只记 `info!("reveal {app}/{id}/{field}")`，绝不记值；把值 `note_session_secret` 一下，让 `redact_known_secrets` 覆盖它（`lib.rs:109-196`）。
- 不做节流、不做二次认证（见决策 A1）。

#### 1.4.2 后端：修 `get_providers` 的主线程阻塞与 Base URL 断链

- `get_providers` 改为 `async fn` + `spawn_blocking`，或者至少把 `block_on` 的凭据管理器访问挪出主线程。为什么现在就改：回显功能会让用户更频繁打开编辑页，`get_providers` 会被更频繁地重取；N 个供应商 × `CredReadW` 在主线程上是可感知的卡顿。
- `secretStatus.baseUrl` 保留在 `get_providers` 里（卡片要用），这是对瘦身方案 §5.2.1"批量读取不碰凭据管理器"的**有意偏离**，理由是 Base URL 的敏感度远低于密钥、用户明确要看，写进 SECURITY.md。
- 顶层 `baseUrl` 防御：`extract_claude` / `extract_codex` 增加"顶层 `baseUrl` 若存在则移除并记 warning"，保证即使前端再出错也不会落 DB。同时为验收记录补一条回归测试。

#### 1.4.3 前端：Base URL 按应用回填到正确位置

`EditProviderDialog.tsx:191-198` 的 `withSecrets` 不再注入顶层 `baseUrl`，改为：

| 应用 | 注入位置 |
|---|---|
| Claude | `settingsConfig.env.ANTHROPIC_BASE_URL` |
| Codex | `settingsConfig.config`（TOML 文本）里当前激活 `[model_providers.<id>]` 的 `base_url`，用已有的 `setCodexBaseUrl` 工具（`utils/providerConfigUtils.ts:1229`） |
| Pi | 顶层 `baseUrl`（现状正确） |

注意：当前供应商编辑时 `liveSettings` 优先于 `withSecrets`（`:199-206`），而 live 读取路径已剥掉 `ANTHROPIC_BASE_URL`（`live.rs:1066`）。所以要么 live 路径保留 Base URL（推荐：它不是密钥，`read_live_provider_settings` 只剥密钥键），要么在 `liveSettings` 之上再叠一次 Base URL。选前者，改一行过滤规则即可。

保存时的往返：Base URL 回填进配置 → 提交 → 提取器照旧剥离并写凭据管理器（同值覆盖，幂等）。不需要新 IPC 字段。

#### 1.4.4 前端：`ApiKeyInput` 的显示按钮

- `configured && !userEdited` 时：输入框显示 8 个圆点占位（`placeholder="••••••••"`，不是 value），右侧**始终**渲染眼睛按钮（去掉 `displayValue &&` 的条件）。
- 点眼睛：调 `providersApi.revealSecret(app, id, "api_key")` → 成功后 `setUserEdited(true)`、`onChange(value)`、`setShowKey(true)`。也就是把真实值灌进现有的受控状态，之后的行为和"用户自己输入了这个值"完全一致：再点眼睛切换遮罩；不改就保存等于同值覆盖。
- 读取失败（凭据管理器不可用 / 条目丢失）：在输入框下方显示错误文案，不清空 `present` 状态。
- 对话框关闭 / 切换供应商：组件卸载即释放；`EditProviderDialog` 的 `initialData` 不会包含密钥（它来自 `get_providers`）。
- Pi 表单接上 `configuredStatus`，行为与 Claude / Codex 一致。
- Codex 的 API Key 状态在 `useCodexConfigState` 里（`auth.OPENAI_API_KEY` / bearer），回显后会同时出现在"原始配置"编辑器里，这是预期（用户要求看到）。

#### 1.4.5 卡片显示 Base URL

`ProviderCard` 读 `secretStatus.baseUrl`，显示 host（`new URL(...).host`），完整 URL 放 `title`。Base URL 为空时显示"官方端点"或不显示。

- 单测（前端）：`ApiKeyInput` 在 `present=true` 时初始 value 为空、眼睛可见；点眼睛后 `reveal` 被调用一次、输入框切到 `text` 且 value 为回显值；再点隐藏；60 秒后自动遮罩（用 fake timers）。改掉 `tests/components/ApiKeyInput.test.tsx:27-44` 现有断言。

## 第 2 部分：端到端加密与零信任

### 2.1 先把词说清楚

cc-switch 是单机桌面应用，没有自己的云端。它唯一把数据交给第三方的地方是 **WebDAV / S3 同步**。所以：

- **端到端加密**：同步载荷在本机加密、在另一台本机解密，WebDAV / S3 服务器（以及中间的 CDN、运维人员、被入侵的存储桶）只见密文。
- **零信任**在本项目里落成四条可验证的属性：
  1. **不信任存储服务器**：它拿不到明文，也不能篡改、回滚、替换快照而不被发现。
  2. **不信任网络**：明文密码不走 http。
  3. **不信任同步载荷**：下载的东西在解密、验签、版本检查之前不碰本地 DB（现有 SQL 导入 authorizer 是最后一道，不是第一道）。
  4. **不信任本机其他进程读取投递值**（可选，见 B5）：提供一种不落 `HKCU\Environment` 的严格投递模式。

**不做**：本地 SQLite 加密（SQLCipher）。DB 里已经没有密钥；给 DB 加密意味着每次打开都要先从凭据管理器取 DB 密钥，凭据管理器不可用时整个应用瘫痪，而收益只是"防止本机同用户的其他进程读到供应商名字与非敏感配置"。BitLocker + DPAPI 已经覆盖了磁盘被拿走的场景（决策 B4）。

### 2.2 现状事实

| 事实 | 依据 |
|---|---|
| 上传三件套 `db.sql`（整库 SQL dump）、`skills.zip`、`manifest.json`；`SYNC_SKIP_TABLES` 与 `SYNC_PRESERVE_TABLES` 都为空，所以 `settings` 表（含 `managed_env_vars`、`known_secret_targets`）也在里面 | `services/sync_protocol.rs:32-34`；`database/backup.rs:86-115` |

### 2.3 目标

- 启用 E2E 后，服务器上只有：一个明文外层 manifest（协议版本、KDF 参数与盐、密文哈希）+ 两个密文 blob。供应商名、Base URL、MCP 命令、prompts、skills 内容全部不可见。
- 篡改任一字节 → 解密失败 → 拒绝应用，本地 DB 不动。
- 服务器把快照换成更早的合法快照（回滚攻击）→ 客户端检测到序号倒退 → 默认拒绝，用户可显式接受。
- 两台机器同时上传 → 后者收到"远端已变化"错误而不是静默覆盖。
- 开启 E2E 后不再允许写入或读取旧的 v2 明文布局（防降级）。

### 2.4 做法

#### 2.4.1 密码学选型

| 项 | 选择 | 为什么 |
|---|---|---|
| AEAD | XChaCha20-Poly1305（`chacha20poly1305` crate，RustCrypto） | 24 字节随机 nonce 可安全随机生成，无计数器管理；纯 Rust、无 unsafe、审计过；比 AES-GCM 少一个"nonce 复用即灾难"的坑 |
| KDF | Argon2id（`argon2` crate），m=64 MiB、t=3、p=1，盐 16 字节随机 | 口令派生的行业默认；参数写进 manifest 便于日后升级 |
| 密钥层级 | 口令 → KEK；每次上传随机生成 32 字节 DEK 加密两个 blob；DEK 用 KEK 以 AEAD 封装后放进 manifest | 改口令只需重封 DEK，不必重加密（虽然现在每次上传都是全量，但这让"多快照历史"未来可扩展） |
| 完整性绑定 | 每个 blob 的 AAD = `format ‖ version ‖ snapshotId ‖ artifactName ‖ seq`；内层 manifest（设备名、创建时间、序号、两个明文哈希）整体作为第三个密文 | 防止把 A 快照的 `db.sql` 拼到 B 快照的 manifest 里 |
| 哈希 | 保留 SHA-256，但对**密文**算，外层 manifest 明文携带；明文哈希放内层 | 服务器端工具仍能做完整性校验，而不知道明文 |
| 不选 `age` | `age` 口令模式用 scrypt，依赖树更大，而且它的格式为多收件人设计，本项目只需要单口令 | — |

内存中的 KEK / DEK 全部 `Zeroizing<[u8; 32]>`；口令本身只在派生时短暂存在。

#### 2.4.2 口令从哪来、存哪

- 设置页"同步加密"区：用户设置一个**同步口令**（与 WebDAV / S3 登录密码无关）。存入凭据管理器 `cc-switch/v1/app/sync/passphrase`（复用 `sync_secrets.rs` 的三态写法）。**口令永不上传**，这是零信任对服务器成立的前提。
- 启动或首次同步时派生 KEK，缓存在 `AppState`（`Zeroizing`），避免自动同步每次都跑 1 秒 Argon2。盐来自远端外层 manifest；远端为空时本机生成新盐。
- 另一台机器：输入同一口令 → 从远端 manifest 取盐 → 派生 → 解密。口令错则 AEAD 认证失败，报"口令不正确或数据已被篡改"（两者刻意不区分）。
- 忘口令 = 远端数据不可恢复。UI 必须在设置口令时用红字说明，并给"重置远端"按钮（删远端、以新口令重传本机快照）。

#### 2.4.3 线上格式：v3

```
{root}/v3/{profile}/
  manifest.json      明文外层：{ format:"cc-switch-sync-e2e", version:3, dbCompatVersion:6,
                       kdf:{alg:"argon2id",m,t,p,salt}, wrappedDek:{nonce,ct},
                       sealed:{nonce,ct}   ← 内层 manifest 密文
                       artifacts:{ "db.sql.enc":{sha256,size}, "skills.zip.enc":{sha256,size} } }
  db.sql.enc
  skills.zip.enc
```

- 内层 manifest：`{ deviceName, deviceId, createdAt, seq, snapshotId, plainHashes:{...} }`。`seq` 为单调递增整数（本机取 `max(本地已知 seq, 远端 seq) + 1`）。
- `sync_protocol.rs` 现在的 `build_local_snapshot` / `download_and_verify` / `apply_snapshot` 结构不动，在其上下各加一层 `seal` / `open`。传输层（WebDAV / S3）完全不感知加密，只是多了 `.enc` 后缀。
- `PROTOCOL_VERSION` 升 3；读到 v2 布局：若本机 E2E 已开启 → 拒绝（防降级），提示"远端是未加密旧快照，请用'迁移远端'"；若未开启 → 现有行为。

#### 2.4.4 回滚与并发保护

- 本机持久化 `last_applied_seq` 与 `last_uploaded_seq`（`settings.json`，设备级）。下载时 `remote.seq < last_applied_seq` → 报"远端快照比本机已应用的更旧，可能是服务器回滚"，提供"仍然应用"按钮（用户显式接受）。
- 上传：WebDAV 在 PUT manifest 时带 `If-Match: <上次 etag>`（首次用 `If-None-Match: *`）；412 → 报"远端已被其他设备更新，请先下载"。S3：AWS 与 R2 已支持 `If-Match` / `If-None-Match` 条件写，MinIO 视版本；不支持时降级为"上传前 HEAD 比较 etag"（尽力而为，写进文档）。先 PUT 两个 blob 再 PUT manifest 的顺序不变，manifest 是提交点。
- 自动同步只上传，因此并发冲突只影响上传；冲突时自动同步停下并在设置页显示状态，不重试覆盖。

#### 2.4.5 传输与零信任的其他收口

- WebDAV：`http://` 默认拒绝，除非主机是 `localhost` / `127.0.0.1` / RFC1918 私网且用户勾选"允许不安全连接"。为什么不是"E2E 开了就允许 http"：Basic 认证的密码仍会明文过线。S3 同理。
- 下载后的验证顺序固定：大小上限 → 密文哈希 → 解封 DEK → 打开内层 manifest → 序号检查 → 解密 blob → 明文哈希 → 现有 `import_sql` authorizer。任何一步失败都不碰本地。
- 应用快照前先做一次 DB 文件备份（`pre-sync-restore-<ts>.db`，纳入 `backup_retain_count` 轮换）。现状只备份 skills（`sync_protocol.rs:369`），DB 靠 SQL 导入的事务性；加一份文件备份让"下载了错的快照"可一键回退。
- 明文护栏 `assert_no_secret_patterns` 继续对**明文** SQL 跑（加密前），不放松。

#### 2.4.6 迁移与兼容

- 设置页新增"启用端到端加密"开关 + 口令设置。开启流程：设口令 → 立即上传一份 v3 快照 → 成功后询问"删除远端 v2 明文快照？"（默认删，因为留着就是明文副本）。
- 其他设备：升级到 2.1 后第一次同步读到 v3 → 弹口令输入 → 派生 → 下载。
- 关闭 E2E：需要重输口令确认，然后上传 v2？**不提供**关闭后的降级上传，只允许"删除远端并停用"。理由：同一远端同时存在密文与明文没有意义。
- `DB_COMPAT_VERSION` 不变（schema 仍 v19）。

#### 2.4.7 可选：严格投递模式（B5）

现状：`HKCU\Environment` 里当前供应商的密钥是明文，本机同用户任何进程都能读。这是瘦身方案接受的边界（SECURITY.md L20-22）。零信任视角下可提供一个开关：

- **严格模式**：切换供应商时**不写** `HKCU\Environment`，只更新 live 文件与 `managed_env_vars` 记录；密钥只经"打开终端"（`Command::env`，`commands/misc.rs:3037-3159`）注入到 cc-switch 自己启动的终端。用户从别处启动的 `claude` / `codex` / `pi` 将拿不到密钥（Codex `env_key` 缺失报错、Pi 未解析变量不可用，都是 fail-closed）。
- 代价：用户体验明显变差（必须从 cc-switch 开终端），所以默认关。做的成本很低：`EnvSink` 已是 trait，加一个 `NoopEnvSink` 并在切换流程按设置选择；托盘和卡片显示"严格模式"徽标。

### 2.6 验收

- 单测（Rust，`sync_e2e` 模块）：seal → open 往返；改密文任一字节 → 失败；错口令 → 失败且错误信息不区分；AAD 错位（拿 A 的 blob 配 B 的 manifest）→ 失败；`seq` 倒退 → 返回专门错误码。
- 单测：v2 远端 + 本机 E2E 开 → 拒绝；v3 远端 + 本机 E2E 关 → 提示输入口令。
- 集成：WebDAV 内存 mock 两台"设备"（两个 `AppState`）并发上传 → 第二个收到 412 类错误。
- 手工：真实 WebDAV（坚果云或本地 `rclone serve webdav`）与真实 S3（MinIO），A 机上传、B 机输入口令还原，供应商列表一致、密钥全部显示"需要密钥"。用抓包或直接看服务器文件确认只有密文。
- `secret-scan.ps1` 扫本地测试 home 与 mock 远端目录：0 命中（远端目录里连供应商名都不该出现，可加一条自定义字面量）。
- SECURITY.md 新增"同步加密"一节：算法、参数、口令不上传、忘口令不可恢复、`http` 策略、B3 的明确否定。

### 4.2 做法

#### 4.2.1 IPC 输入收口（S-1 ～ S-4）

- **S-1**：`load_messages` 复用 `delete_session` 的 `provider_roots` + `canonicalize` + `starts_with` 检查；不在根目录内直接拒绝。会话列表本来就是后端枚举出来的，前端没有理由传别的路径。
- **S-2**：把"选文件 + 导出"合并成一个后端命令 `export_config_via_dialog()`，对话框在 Rust 侧弹、路径不经前端往返；导入同理。原来的 `save_file_dialog` / `open_file_dialog` 若无其他调用者则删除。为什么不做路径白名单：用户可以选任意目录，白名单没有意义；把路径来源固定为系统对话框才是正确的边界。
- **S-3**：`launch_session_terminal` 入参改为 `{ app, session_id, cwd }`，命令行由后端按 `app` 拼（`claude --resume <id>` 等），`session_id` 校验为 `[A-Za-z0-9._-]+`，`cwd` 走与 `open_provider_terminal` 相同的 `resolve_launch_cwd`（`misc.rs:2992-3015`）。`custom_config` 若是用户在设置里保存的自定义终端命令，则从设置读，不由前端传。
  - **施工决定（2026-09-20，P1 期间）**：**P1 不做，并入 P2 的 C5**。实测依据：前端 `SessionManagerPage.tsx:425` 有 `if (!isMac())` 守卫，Windows 上只把 resume 命令复制到剪贴板，根本不调用该命令；后端 `session_manager/terminal/mod.rs:13-15` 在非 macOS 上先返回 `Err("Terminal resume is only supported on macOS")`，`command` 字符串在 Windows 上从不被执行。也就是说 S-3 在唯一支持平台（D1 仅 Windows）上没有可达路径，加固的是 C5 即将整块删除的代码。
- **S-4**：`open_external` 后端用 `url::Url::parse` 校验，只放行 `http` / `https`，其余返回错误；删掉自动补 `https://` 的行为（调用方都传完整 URL）。`DatabaseUpgrade.tsx` 改走 `settingsApi.openExternal`。
- 顺手：所有接受 `String` 路径的命令列一张表放进 SECURITY.md"IPC 路径参数"段，逐条写"来源 = 系统对话框 / 后端枚举 / 用户设置"。

#### 4.2.2 供应链与发布（S-5 ～ S-8）

- **S-5**：新增 `.github/workflows/audit.yml`：每周一 + 手动触发，跑 `cargo deny check advisories licenses bans`（`deny.toml` 入库）与 `pnpm audit --audit-level=high`；只报告、不阻塞主 CI（用户已明确不要 Dependabot 制造分支）。CI 主流程加 `cargo deny check advisories` 作为必过项，因为它只读 lockfile、几秒钟。
- **S-6**：`secret-scan.ps1` 保留夹具扫描；CI 再加 `gitleaks` action（默认规则集，`.gitleaks.toml` 豁免 `src-tauri/tests/fixtures/`）。两者职责不同：前者证明夹具没漏，后者证明没人提交真密钥。
- **S-7（D1）**：默认方案是**发布时附 `SHA256SUMS` + `minisign` 签名**，公钥写进 README 与 SECURITY.md，`release-process-zh.md` 加签名步骤；SmartScreen 警告在 README"下载安装"里如实说明。为什么不是代码签名证书：OV 证书年费 + 硬件 token 或 Azure Trusted Signing 月费，对个人 fork 不划算；minisign 已能让用户验证"这个包是维护者发的"。
- **S-8**：`cargo tree -i reqwest@0.13` 找出来源；若是某个 Tauri 插件的可选特性，关掉；若不能关，记录到 SECURITY.md 依赖段。目标是 `cargo tree` 里只有一份 reqwest 且无 `native-tls`。
- GitHub Actions 全部按 commit SHA 固定（现在是 `@v6` 这类浮动 tag）。

#### 4.2.3 本地文件 ACL（S-10，可选）

在首次创建 `~/.cc-switch` 时对目录设置 DACL：只保留当前用户 + SYSTEM + Administrators，去掉继承。实现用 `windows-sys` 的 `SetNamedSecurityInfoW`（一处 FFI）或调用一次 `icacls`（子进程）。瘦身方案 S12 当时判断"文件不含密钥，不做"；现在的理由变了：DB 里有供应商名、Base URL 的历史（Codex 非激活表）、MCP 命令、prompts，属于用户隐私而非密钥。收益中等、成本半天，默认做（D2）。

#### 4.2.4 稳定性（T-1 ～ T-8）

- **T-1**：见 1.4.2。
- **T-2**：`lock_writes` 改为 `lock().unwrap_or_else(PoisonError::into_inner)`，或映射为 `AppError::Lock`。凭据管理器的一次 panic 不该让后续所有保存都 panic。
- **T-3**：`WindowsSecretStore::get/set/delete` 对 `SecretError::Backend` 做最多 3 次、间隔 50 / 100 / 200 ms 的重试；`NoEntry`、`TooLong` 不重试。为什么：`CredReadW` 在登录会话切换、锁屏解锁瞬间偶发 `ERROR_NO_SUCH_LOGON_SESSION`，重试一下就好，而现在直接给用户报错。
- **T-4**：`PRAGMA busy_timeout = 5000`；启动时 `PRAGMA quick_check`，失败则走现有的 DB 初始化错误对话框并提供"从最近备份恢复"。**不启用 WAL**：README 明确支持把配置目录放在 Dropbox / OneDrive / NAS，并有 WSL2 UNC 路径契约测试；WAL 在网络文件系统与云同步目录上会损坏，`-wal` / `-shm` 副文件也会被同步工具搬来搬去。回滚日志模式是这个部署场景下的正确选择，把这个理由写进代码注释。
- **T-5**：`apply_snapshot` 在 SQL 导入前先 `backup_database_file`（命名 `pre-sync-restore-<ts>.db`），纳入轮换。与 2.4.5 合并做。
- **T-6**：**执行真机升级 20 步并填表**。这是 2.0.0 最大的未验证风险：迁移代码只在夹具上跑过。做法：找一台装过 3.20.3 的机器或在虚拟机里装 3.20.3 → 配 3 个供应商 → 覆盖装 2.0.0 → 逐条勾。发现问题先修再进 2.1。
- **T-7**：补集成测试：把 `~/.pi/agent/models.json` 设只读 → 启动流程 → 断言 `live_reapply_pending == "1"` 且报告含该文件 → 恢复可写 → 再跑 → 清零。`EnvSink` 已挂 `AppState`，注入点齐备。
- **T-8**：ci.yml 的 clippy 加 `--all-targets`，与验收记录的本地命令对齐。
- 环境变量切换的事务性：切换流程"先删旧、再写新"（`services/provider/mod.rs:781-826`），写新失败时只有 live 写入失败才 `undo`。补一条：写新变量失败也要把旧变量（切换前读到的值，`Zeroizing` 暂存）写回，避免"旧的删了、新的没写上"的中间态。
- 诊断：About 页加"复制诊断信息"（版本、schema 版本、迁移标志、`known_secret_targets` 条数、最近 50 行脱敏日志、`crash.log` 是否存在）。用户报 issue 时有东西可贴，而不用翻目录。
