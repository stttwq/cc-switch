# 5.1 Configuration Files

## CC Switch Data Storage

### Storage Directory

Default location: `~/.cc-switch/` (on Windows that is `%USERPROFILE%\.cc-switch\`)

Customizable location in settings (for cloud sync).

### Directory Structure

```
~/.cc-switch/
├── cc-switch.db      # SQLite database (SSOT, contains no secrets)
├── settings.json     # Device-level settings (contains no secrets)
├── logs/             # Runtime logs (redacted)
├── crash.log         # Crash records
├── skills/           # Skill SSOT directory
├── skill-backups/    # Skill backups (created on uninstall)
└── backups/          # Database backups
```

### Where the Credentials Live

**Not in these files.** API keys, endpoint URLs and environment variables judged sensitive are persisted only in **Windows Credential Manager**, under entry names prefixed with `cc-switch/`. The database, `settings.json`, export files, sync payloads and logs contain no secret values.

### Database Contents

`cc-switch.db` is a SQLite database that stores:

| Table | Contents |
|-------|----------|
| providers | Provider configurations (keys and endpoint URLs stripped) |
| mcp_servers | MCP server configurations |
| prompts | Prompt presets |
| skills | Skill installation status |
| skill_repos | Skill repository configurations |
| profiles | Configuration snapshots |
| settings | App settings and the record of environment variable ownership |

### Device Settings

`settings.json` stores device-level settings:

```json
{
  "language": "zh",
  "theme": "system",
  "minimizeToTrayOnClose": true,
  "launchOnStartup": false,
  "visibleApps": { "claude": true, "codex": true, "pi": true },
  "claudeConfigDir": null,
  "codexConfigDir": null,
  "piConfigDir": null,
  "skillSyncMethod": "auto",
  "skillStorageLocation": "cc_switch",
  "backupIntervalHours": 24,
  "backupRetainCount": 10,
  "preferredTerminal": "wt"
}
```

These settings are not synced across devices. The WebDAV password and the S3 Access Key are not here either — they live in Windows Credential Manager.

### Automatic Backups

The `backups/` directory stores automatic backups:

- Created on schedule (interval and retention count configurable)
- Retains the most recent 10 backups by default
- File names include timestamps
- Backups contain no keys now, so they are safe to keep and share

Upgrades additionally produce a `pre-secrets-migration-*.db` file (the pre-migration v18 database, which still holds plain text). It exists only for rollback and is never deleted automatically.

## Environment Variable Delivery

CC Switch writes **user-level** environment variables only (registry `HKCU\Environment`), never `HKLM`, and broadcasts `WM_SETTINGCHANGE` after a batch write.

| Purpose | Variable Name |
|---------|---------------|
| Claude API key | `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_API_KEY` |
| Claude endpoint | `ANTHROPIC_BASE_URL` |
| Codex third-party API key | `CC_SWITCH_CODEX_API_KEY` |
| Codex official API key | `OPENAI_API_KEY` |
| Pi API key | `CC_SWITCH_PI_<KEY>_API_KEY` |
| Pi sensitive headers | `CC_SWITCH_PI_<KEY>_HEADER_<NAME>` |

Which variables were written by CC Switch is recorded in the `managed_env_vars` key of the `settings` table.

## Claude Code Configuration

### Configuration Directory

Default: `~/.claude/`

### Key Files

```
~/.claude/
├── settings.json     # Main configuration file
├── CLAUDE.md         # System prompt
└── skills/           # Skills directory
    └── ...
```

### settings.json

```json
{
  "env": {
    "ANTHROPIC_MODEL": "kimi-k2.7-code",
    "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "262144"
  }
}
```

> ⚠️ **Note**: When writing this file, CC Switch no longer includes `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL`. Claude Code reads those straight from the process environment, so they are delivered as environment variables. A guard runs before each write and refuses it if a sensitive key is detected.

If you wrote `env.ANTHROPIC_*` yourself in `~/.claude/settings.local.json` or in a project-level `.claude/settings.json`, **those override the process environment variables**. CC Switch does not modify those files; it only emits a read-only conflict warning.

### MCP Configuration

MCP server configuration is in `~/.claude.json`:

```json
{
  "mcpServers": {
    "mcp-fetch": {
      "command": "uvx",
      "args": ["mcp-server-fetch"]
    }
  }
}
```

## Codex Configuration

### Configuration Directory

Default: `~/.codex/`

### Key Files

```
~/.codex/
├── auth.json         # Your own Codex sign-in state (not written by CC Switch)
├── config.toml       # Main configuration + MCP
├── AGENTS.md         # System prompt
├── skills/           # Skills directory
└── sessions/         # Session records
```

### config.toml

```toml
model_provider = "custom"
model = "gpt-5.2"

[model_providers.custom]
name = "custom"
base_url = "https://api.example.com/v1"
wire_api = "responses"
env_key = "CC_SWITCH_CODEX_API_KEY"
```

| Field | Description |
|-------|-------------|
| `env_key` | A string naming the user environment variable that holds the key; the key value itself is not in the file |
| `base_url` | Endpoint URL. **Exception**: the Codex CLI does not support variable references in this field, so the Base URL of the currently active provider is written here; the base URLs of all other providers stay in Credential Manager |

> ⚠️ CC Switch no longer writes `~/.codex/auth.json`, and it no longer writes `experimental_bearer_token` into `config.toml`.

## Pi Configuration

### Configuration Directory

Default: `~/.pi/agent/`

### Key Files

```
~/.pi/agent/
├── models.json       # Provider and model configuration
├── AGENTS.md         # System prompt
├── skills/           # Skills directory
└── sessions/         # Session records
```

### models.json

```json
{
  "providers": {
    "example": {
      "baseUrl": "https://api.example.com/v1",
      "apiKey": "$CC_SWITCH_PI_EXAMPLE_API_KEY"
    }
  }
}
```

`apiKey` is always in `$VARIABLE_NAME` form. `baseUrl` is an exception just like in Codex — the Pi CLI does not support variable references in that field, so enabled providers carry the plain address.

## Configuration Priority

CC Switch's priority when modifying configurations:

1. **Windows Credential Manager** - Single source of truth for keys and endpoint URLs
2. **CC Switch Database** - Single source of truth (SSOT) for everything else
3. **Live configuration files / user environment variables** - Written when switching providers
4. **Backfill Mechanism** - Reads from live files when editing the current provider (backfills only the stripped part)

## Manual Configuration Editing

### Safe to Edit Manually

- CLI tool configuration files (the non-sensitive parts will be backfilled by CC Switch)
- CC Switch's `settings.json`

### Not Recommended to Edit Manually

- `cc-switch.db` database file
- Backup files

### Sync After Editing

If you manually edit CLI tool configurations:

1. Open CC Switch
2. Edit the corresponding provider
3. You will see the manual changes have been backfilled
4. Save to sync to the database

> ⚠️ If you hand-wrote a plain-text key into a live file, CC Switch extracts it into Credential Manager during read/sync and replaces the value in the file with a variable reference.

## Configuration Migration

### Migrating from Older Versions

The migration completes automatically on first launch after upgrading to the current version (database schema v19):

1. Create the `pre-secrets-migration-*.db` rollback backup
2. Delete the providers / MCP / skills rows of the removed apps, plus the local routing tables
3. Move every provider key and endpoint URL into Windows Credential Manager and strip them from the database
4. Move the WebDAV password and the S3 Access Key into Credential Manager
5. Clean up legacy plain-text leftovers: `config.json` and its `.bak` / `.migrated` files, `codex_oauth_auth.json`, `backups/env-backup-*.json`, `%TEMP%\claude_*.json`
6. Rewrite the live files and deliver the environment variables
7. Show a one-time dialog describing the migration result

The migration is idempotent; if interrupted it runs again on the next launch. When Credential Manager is unavailable the migration is blocked with an error — it never falls back to writing plain text.

### Cross-device Migration

1. Export configuration on the source device
2. Import configuration on the target device
3. Or use the cloud sync feature

> ⚠️ Neither exports nor syncs **carry keys**. On the target device every provider shows the "needs key" badge, and you must re-enter each API Key before switching to it.

## Configuration Backup Recommendations

### Regular Backups

It is recommended to regularly export configurations:

1. Settings > Advanced > Data Management
2. Click "Export"
3. Save to a secure location

### Backup Contents

The export file includes:

- All provider configurations (without keys)
- MCP server configurations
- Prompt presets
- App settings

### Not Included

- Any keys or endpoint URLs (they live in Windows Credential Manager)
- Device-level settings (not suitable for cross-device)
